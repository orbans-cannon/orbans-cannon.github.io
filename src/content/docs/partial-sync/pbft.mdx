## 反例：拿掉 commit 階段

如果協議在 prepared 時就執行，不再等 commit，safety 會被一個拜占庭 primary 加上 GST 前的訊息延遲破壞。

**節點編號。** PBFT 原文規定 view $v$ 的 primary 是編號 $p=v \bmod |R|$ 的副本。令 B、C、D、A 依序為 0、1、2、3，則 view 0 的 primary 是 B，view 1 的 primary 是 C，而 C 是誠實的。

**這些步驟用到的規則。** 這些規則已對照 PBFT 期刊版（TOCS 2002，§4.3–4.5 與 Figure 4）：prepared 要求 pre-prepare 加上 $2f$ 份相符的 prepare；新 view 的 primary 把 VIEW-CHANGE 收進集合 $S$（每份需要 $2f-1$ 份來自其他副本的 VIEW-CHANGE-ACK 佐證，本追蹤略去這些 ack），當 $S$ 中有 $2f+1$ 份 $P$ 沒有序號 $n$ 的項目（且 $h<n$）時，對該序號選 null 請求（Figure 4 條件 B）。注意：D 在 view 0 送過 PREPARE，所以它的 VIEW-CHANGE 的 $Q$ 集合含有 $m$；決定程序的條件 B 只看 $P$，所以不影響結論。整個反例是對「拿掉 commit 階段」這個假想協議所寫，**作者還沒有逐步驗證**，所以狀態是草稿。

**為什麼真正的 PBFT 不會出事。** 真正的 PBFT 要求 A 收到 $2f+1$ 份 commit 才執行（committed-local），代表至少 $f+1$ 個誠實節點已經 prepared。任何 $2f+1$ 份 view-change 與這 $f+1$ 個誠實節點至少交集 $(2f+1)+(f+1)-(3f+1)=1$ 個節點，它是誠實的，會在 view-change 裡帶出 prepared 證明，新 primary 因此不會填 null。這正是 [Quorum 交集](/impossibility/quorum/#lemma-intersection-size)的應用。

<div slot="conclusion">
在序號 $n$ 上，誠實節點 A 執行了 $m$，誠實節點 C、D 執行了 null，違反 **Agreement（Total order）**：不同的誠實節點在同一個序號執行了不同的內容。整個反例只用了一個拜占庭節點 B，剛好是 $f=1$，且所有訊息延遲都發生在 GST 之前。
</div>
