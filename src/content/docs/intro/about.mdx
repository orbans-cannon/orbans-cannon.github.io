## 為什麼做這個網站

<Term id="bft">拜占庭容錯</Term>（Byzantine Fault Tolerance, BFT）的中文資料，多半停在「拜占庭將軍問題」的故事，或是某一個區塊鏈協議的實作導覽。要讀懂論文裡的 **模型、證明與下界**，中文世界幾乎沒有銜接的材料，本站希望能補上這些內容的介紹。

## 本站的定位

- **讀者**：有分散式系統基礎、至少知道<Term id="consensus" tip="萬一你還不知道：共識是指一群各有意見的電腦，要一起決定同一件事（例如一筆帳該不該記下去），而且決定之後大家的結果必須一致。難處在於其中有些電腦可能故障或說謊。「什麼是拜占庭？」那一頁會從頭講起。">共識基本概念</Term>的人。讀完本站的內容，大約能獨立讀懂分散式計算會議（如 PODC、DISC）上的 BFT 論文，並說得出它的結論在什麼模型下成立。
- **重理論、輕實作**：重點是「在什麼模型下，什麼性質可以或不可以被保證」，不是如何部署某個系統。實作教學已經很多，本站不重複。
- **不是論文翻譯**：不轉載論文，只寫講解、直覺與證明拆解，並連結原文。

## 本站的組織原則：先分清模型

多數教材把 PBFT、HotStuff、HoneyBadger、Bullshark 並排介紹，讀者容易以為它們只是「同一個問題的不同解法」。實際上它們屬於 **不同的時序假設**，能做的事、證明的方式、複雜度的意義都不同。

因此本站的主體不是依年代或依系統排列，而是先用一個獨立的部分講清楚每個模型下的極限，再依模型分成三條主線，最後讓它們在 DAG 協議處合流：

| 部分 | 內容 | 開場問題 |
| --- | --- | --- |
| 入門 | 問題、性質與模型的定義 | 說「大家達成共識」，精確來說要保證哪些事？ |
| 不可能性與下界 | FLP、FLM、DLS、Dolev–Strong 等 | 每個模型下什麼做不到？ |
| <Term id="sync">同步</Term> | 延遲有已知上界 Δ | <Term id="signature">簽章</Term>改變了什麼？ |
| <Term id="psync">部分同步</Term> | <Term id="gst">GST</Term> 之後才有上界 | 為什麼 <Term id="safety">safety</Term> 與 <Term id="liveness">liveness</Term> 要分開？ |
| <Term id="async">非同步</Term> | 沒有任何時間假設 | FLP 之後，隨機化如何繞過它？ |
| 合流 | 以 DAG 組織訊息的協議（DAG-BFT） | 把「傳播資料」和「決定順序」分開，能換到什麼？ |
| 前沿 | 2025–26 的新作 | 還有哪些問題沒解決？ |

不可能性與下界之所以獨立成一部分，是因為它收錄的論文最難、證明技巧各不相同，需要足夠的篇幅。後面三條主線都會回頭引用它的結論。

## 每頁怎麼讀

每個協議或定理頁開頭，都有一張小卡片，先交代這個結論是在什麼條件下成立的：網路有多可靠、有沒有數位簽章、壞節點能做什麼。內文再依序講：條件、保證了什麼、為什麼成立、拿掉哪個條件就不成立。

文中出現「需要多少通訊量」這類數字時，都會寫清楚是在算什麼（例如訊息的個數），以及是在哪種情況下算的（例如領導者是不是好人），這樣兩個協議的數字才能放在一起比。

### 頁面狀態標籤

> 入門各頁已經完成，不顯示標籤；其他部分的頁面還在寫，仍依下表標示。這一小節是開發期的說明，全站完成後會刪除。

尚未完成的頁面在側欄有一個標籤，表示它走到哪個階段。一共五個階段，由左到右：

| 階段 | 標籤 | 意義 |
| --- | --- | --- |
| 0 | **大綱** | 只有章節標題與「預計涵蓋」，沒有內容 |
| 1 | **規劃中** | 有模型卡、預計涵蓋與少量示範，但沒有完整正文 |
| 2 | **草稿** | 有完整正文，但尚未逐條對照原文，或已對照但作者還沒審過 |
| 3 | **部分核對** | 部分敘述已對照出版版原文；沒核對的地方在頁面裡標明 |
| 4 | **已核對** | 所有敘述都已對照出版版原文，且作者審過；完成後標籤拿掉（入門各頁即是） |

參考文獻裡標「†」的條目，表示它的書目資訊（標題、作者、年份、出處）本身還沒核對。

## 回報錯誤與聯絡

發現錯誤或有建議，可以用下面兩種方式：

- **開 issue**：到本站 GitHub repo 的 [Issues 頁](https://github.com/orbans-cannon/orbans-cannon.github.io/issues)，寫下頁面網址與你認為哪裡不對。大多數情況請用這個，因為其他讀者看得到，也不會重複回報。
- **送 pull request**：如果是錯字或你已經知道怎麼改，直接改檔案送 PR 最快（每頁底部有「編輯頁面」連結，會帶你到 [repo](https://github.com/orbans-cannon/orbans-cannon.github.io)）。
